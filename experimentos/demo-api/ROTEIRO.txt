ROTEIRO DA DEMONSTRAÇÃO — AuthFix
==================================

Ideia em uma frase:
  Uma API tem um endpoint de administrador sem proteção. O Semgrep detecta,
  o AuthFix localiza o problema, reaproveita a regra de autorização que já
  existe no projeto, valida a correção num contêiner isolado, e a falha some.


------------------------------------------------------------
ANTES DE COMEÇAR (fazer 15 min antes)
------------------------------------------------------------

[ ] Docker Desktop aberto e rodando.
[ ] Abrir DOIS terminais, os dois nesta pasta:

      cd ~/Documents/TCC/experimentos/demo-api

[ ] Garantir que está tudo no estado vulnerável:

      sh demo.sh reset

[ ] Garantir que nenhuma API antiga está rodando (se der "address already in use"):

      lsof -nP -iTCP:5080 -sTCP:LISTEN
      kill <PID que aparecer>

[ ] Aumentar a fonte dos terminais (Cmd +) para a banca enxergar.


------------------------------------------------------------
PASSO 1 — Apresentar a API (Terminal 1)
------------------------------------------------------------

Subir a API:

      dotnet run --urls http://localhost:5080

O que falar:
  "Esta é uma API simples em ASP.NET. Tem uma rota pública, uma de usuário
   e duas de administrador. A autenticação é simulada pelo cabeçalho
   X-Demo-Perfil (User ou Admin)."

Se quiser mostrar o código: Controllers/InformacoesController.cs
  - /api/oi            -> [AllowAnonymous]                    público
  - /api/user          -> [Authorize]                         usuário logado
  - /api/admin-status  -> [Authorize(Policy="SomenteAdmin")]  protegido
  - /api/admin-info    -> NADA                                <- A FALHA


------------------------------------------------------------
PASSO 2 — Mostrar o problema (Terminal 2)
------------------------------------------------------------

      curl -i -H 'X-Demo-Perfil: User' http://localhost:5080/api/admin-status

  Esperado: 403 Forbidden  (esta está protegida, correto)

      curl -i -H 'X-Demo-Perfil: User' http://localhost:5080/api/admin-info

  Esperado: 200 OK  (usuário comum lendo informação de admin!)

      curl -i http://localhost:5080/api/admin-info

  Esperado: 200 OK  (até SEM login nenhum!)

O que falar:
  "As duas rotas são de administrador, mas na segunda o desenvolvedor
   esqueceu a policy. Qualquer pessoa, até anônima, lê a informação.
   Isso é a CWE-862, Missing Authorization — parte do Broken Access Control,
   primeiro lugar no OWASP Top 10."

------------------------------------------------------------
FECHAMENTO — como seria no mundo real
------------------------------------------------------------

  "Na demo eu rodo por script para mostrar cada etapa. No mundo real isso
   roda no pipeline de CI, como o GitHub Actions: a cada Pull Request o
   Semgrep analisa, o alerta aparece na aba Security do GitHub, o AuthFix
   gera e valida a correção e abre um PR para revisão. Nenhuma correção
   entra sem aprovação humana."


------------------------------------------------------------
PERGUNTAS PROVÁVEIS
------------------------------------------------------------

P: Quem escreveu a correção?
R: Nesta demo, a correção está numa resposta simulada, escrita à mão.
   O objetivo é mostrar que o AuthFix verifica se a correção funciona antes
   de confiar nela, venha de um LLM ou de qualquer outra fonte. A integração
   com o LLM é o próximo passo.

P: O que é o Roslyn?
R: O compilador oficial do C#, usado como biblioteca. Ele entende a estrutura
   do código (árvore sintática), então acha o método exato e as regras de
   autorização sem depender de busca por texto.

P: Tem RAG?
R: A recuperação de contexto hoje é estrutural, feita pelo Roslyn, sem
   embeddings. Para código faz sentido: o que se busca são as políticas
   de autorização que já existem no projeto.

P: O que é SARIF?
R: Formato padrão (OASIS), em JSON, para resultados de análise estática.
   Como o AuthFix lê SARIF, não fica preso ao Semgrep.

P: Dá para usar SonarQube?
R: Sim. O SonarQube importa SARIF para visualização. Como fonte de alertas,
   seria preciso um adaptador que converta os alertas dele, que hoje
   não existe no protótipo. Escolhi o Semgrep por permitir regras
   específicas de autorização em ASP.NET e gerar SARIF direto.

P: O que são as condições A, B e C?
R: O quanto de contexto vai para o gerador:
     A = só o método com o alerta
     B = o arquivo inteiro
     C = o arquivo + trechos de autorização recuperados do projeto
   A hipótese é que C gera correções mais aderentes ao padrão do projeto.

P: Por que contêiner sem rede na validação?
R: O patch e o projeto podem ser não confiáveis. Sem rede e com recursos
   limitados, o teste não vaza dados nem baixa nada.


------------------------------------------------------------
SE ALGO DER ERRADO
------------------------------------------------------------

"address already in use"
    -> já tem uma API rodando. Ctrl+C no outro terminal, ou:
       lsof -nP -iTCP:5080 -sTCP:LISTEN
       kill <PID>

Docker não responde / erro no Semgrep
    -> abrir o Docker Desktop, esperar ficar verde, rodar de novo.

Quero recomeçar do zero
    -> sh demo.sh reset
       (desfaz a correção e limpa a pasta saida/)

Plano B (se tudo travar):
    -> mostrar saida/relatorio.md de um ensaio anterior. Por isso,
       ensaie hoje e NÃO rode reset depois do último ensaio, só antes
       de apresentar. Ou guarde uma cópia:
       cp -r saida ~/Desktop/saida-ensaio
